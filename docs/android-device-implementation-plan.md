# Android device implementation plan

Research and implementation proposal for the Rebroid operator console and services. A durable device ID identifies the resource a user owns. A short-lived attachment identifies the specific Android instance a viewer or workflow may control. The first proof is a USB phone and a TCP VM that can be viewed, disconnected and safely replaced while the managed Redroid viewer still works.

## What ships in the first release

An operator can provision a managed device, or register an existing Android phone or VM reachable from the Rebroid host. The reference deployment is a native Linux host. Support two explicit enrollment choices, a host-attached USB device and an existing ADB TCP listener at a literal IP and port. Modern Android wireless pairing with a pairing code is a separate follow-up. The VM owner supplies and boots the guest. The word *app* remains appropriate for APKs, Android package names and commands that act on installed applications. [Deployment baseline](deployment.md#host-requirements) · [Android debugging transports](https://developer.android.com/tools/adb)

These are proposed release defaults. The existing owner and group model remains the authority for access. Administrators configure exact permitted TCP destinations and USB access at deployment. Accounts with the enrollment privilege register approved TCP devices for themselves. Only administrators can discover or enroll USB devices, and only the enrolling administrator can operate their USB device. Each registration has one transport. Make external enrollment opt-in per deployment. Managed-device creation stays available with its current permissions. [Account and authorization model](web-security.md#authorization) · [Current permission catalog](../apps/web/src/shared/permissions/permissions.ts)

| Operation | Managed runtime | Connected phone or VM |
| --- | --- | --- |
| Lifecycle | Provision, start, stop, recreate, clone, remove | Register, confirm attachment, disconnect, reconnect, forget. Forget ends access and removes Rebroid metadata. Device data and power stay under the owner's control. |
| Display and input | Existing main and virtual surface policy | Main display over the verified transport. View, control, screenshot and clipboard each follow their grant. Offer audio only when supported. Require an explicit action to open the phone viewer. |
| Storage and software | Existing APK installation, profiles, live files and stopped-volume operations | No APK provisioning, profile switching, file browser, volume operations or file automation in v1. Existing installed packages can be addressed by supported workflow steps using an explicit package name. |
| Diagnostics and networking | Container logs, Android logs where available, Docker terminal, firewall and resource metrics | Connection status and bounded on-demand logcat with permission. Label egress as managed by the device owner. Docker administration and host firewall enforcement apply only to managed containers. |
| Workflows, OCR and AI | Existing operations, including authorized startup/profile selection | Attach to a confirmed connection. Allow supported observation and input steps with account permissions and independent feature gates. Reject incompatible steps before dispatch. Keep human raw shell and AI shell escalation off for external devices in v1. |

Current behavior is distributed across the [runtime services](../apps/orchestrator/src/android-apps/runtime/services), [automation command implementations](../apps/orchestrator/src/automations/commands), [display controls](../apps/orchestrator/src/android-apps/viewer), and [feature registry](../apps/orchestrator/src/feature-flags/feature-flag.registry.ts). Device capabilities describe support. Each server operation also checks ownership, account permissions, feature state and live attachment identity.

## Runtime providers and external ADB transport

**Existing behavior.** The orchestrator owns application definitions, lifecycle reservations, profile volumes and Docker network attachment. Its managed runtime vocabulary includes both Redroid and generic images. The provisioning path prepares Android remote access only for Redroid. Display-sidecar ADB commands select a target by serial with `-s`, and viewer startup can call `adb connect` on that value. A USB serial and an IP endpoint require different admission paths. [Orchestrator architecture](orchestrator-architecture.md) · [Runtime image metadata](../packages/android-application-core/src/redroid-runtime.ts) · [Android provisioning](../apps/orchestrator/src/android-apps/provisioning/services/android-apps-provisioning-android.service.ts) · [ADB service](../apps/display-sidecar/src/modules/adb/adb.service.ts)

**Proposed boundary.** Give each device a stable Rebroid ID and owner. Use the existing managed ID as the device ID wherever a managed record is adapted. Resolve managed Android capabilities from the existing runtime rules. A generic container without ADB retains its existing lifecycle and diagnostics. Give external registrations their own typed TCP or USB configuration and connection state. The orchestrator owns registration and capability admission. The display sidecar owns discovery, ADB commands, target leases and scrcpy. Managed Docker operations remain behind the current ports. Removing an external registration revokes work and forgets the attachment. ### Binding a session to the intended device

ADB selects a live transport with `-t ID`. AOSP allocates IDs from a process-local counter starting at one. Its TCP reconnect handler can also register the same transport object again. A USB serial, model, guest property, IP address or numeric transport ID can recur on another handset or VM. Legacy TCP leaves traffic unencrypted. Standard Android wireless pairing authorizes the host key, and the AOSP host-side TLS implementation cited here accepts any server certificate. [ADB command reference](https://android.googlesource.com/platform/packages/modules/adb/+/refs/heads/main/docs/user/adb.1.md) · [Transport allocation, reconnect and TLS verification](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/transport.cpp) · [ADB Wi-Fi architecture](https://android.googlesource.com/platform/packages/modules/adb/+/refs/heads/main/docs/dev/adb_wifi.md)

**Proposed attachment binding.** The sidecar issues an opaque lease binding the registration revision, ADB server incarnation, selected transport ID and uninterrupted attachment. Give each supervised external ADB server incarnation a private socket address and prevent clients from auto-starting a replacement behind that address. Select the transport at dispatch for every operation, including shell, push, forward and cleanup. Allow only the supervised external ADB process to open the approved USB device nodes, including when the managed ADB server is running. For external TCP, use a broker-owned single-connection relay to the approved endpoint that refuses a second upstream connection. This prevents ADB's reconnect loop from silently transferring an old lease. Close consumers, invalidate pending commands and require confirmation after detachment, observation loss, server restart or sidecar replacement. Automatic reattachment defaults off.

**Proposed confirmation.** Discover only administrator-approved TCP addresses and locally visible USB candidates. On a trusted network, an operator can verify a legacy VM by placing a one-time challenge at a fixed guest path through the **hypervisor console**. An enrollment-only read checks it on the selected transport. For host USB, let an attending operator select the just-plugged device on an approved physical port and confirm the handset's host-key prompt during that attempt. For a previously authorized phone, verify the physical port by an attended unplug/replug and confirm the newly observed candidate. Cancel ambiguous attempts. A phone on preconfigured TCP can also be confirmed at first enrollment. Serialize the attempt, show the external ADB host-key fingerprint, and have the attending operator match it to the newly displayed phone prompt. Require the corresponding unauthorized-to-ready transition on that same uninterrupted connection. An already-trusted TCP phone with no fresh prompt needs independent verification, such as a deployment-controlled authenticated path. Offer USB enrollment when verification is unavailable. Expire challenges and bind confirmation to that lease before granting viewer or command access. A manual check addresses accidental endpoint substitution. An untrusted network also requires an authenticated encrypted path. [Android device authorization](https://developer.android.com/tools/adb) · [Legacy TCP properties](https://android.googlesource.com/platform/packages/modules/adb/+/refs/heads/main/docs/dev/adb_wifi.md)

### Deployment and display

- **TCP and USB.** V1 accepts a preconfigured ADB IP and port or an explicitly selected Linux host USB device. USB discovery uses the local server's inventory and reports authorization and permission failures. Enable USB debugging, approve the host key on the handset, and scope host udev permissions and container device access to intended hardware. Test unplug/replug and changing device nodes. Docker Desktop USB/IP needs separate platform verification. Defer Android wireless pairing, with distinct pairing and connection ports, until the shipped ADB version and peer-verification flow are tested. The image currently installs Debian Bookworm's ADB package. [Android hardware setup](https://developer.android.com/studio/run/device) · [Docker device access](https://docs.docker.com/reference/cli/docker/container/run/#using-dynamically-created-devices---device-cgroup-rule) · [Docker Desktop USB/IP](https://docs.docker.com/desktop/features/usbip/) · [Sidecar image](../apps/display-sidecar/Dockerfile) · [Bookworm package](https://packages.debian.org/bookworm/adb)
- **Key persistence.** Mount a private named volume for the external ADB server's Android configuration directory, including its host key and any future pairing state. Apply identical mounts and opted-in USB access in Compose and orchestrator creation/repair. Keep the server socket private and create fresh leases on replacement. Verify both recreation paths retain the host-key fingerprint. Rotation requires reauthorization. [Compose](../deploy/compose.yaml) · [Sidecar creation](../apps/orchestrator/src/docker/sidecar/services/docker-sidecar.service.ts) · [ADB host key](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/client/auth.cpp) · [Pairing store](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/client/adb_wifi.cpp)
- **scrcpy.** Select ADB forward per external lease. Rebroid's direct implementation opens a fresh TCP connection to adbd and rejects an authentication challenge. Forward uses the selected ADB transport for all scrcpy sockets. Keep the external ADB server and forward listener in the sidecar's network namespace. A remote host server would also need a secured path to its forwarded sockets. Preserve managed direct/forward selection and the existing launch, listener, socket-read and cleanup order. Require manual Redroid, TCP VM and USB phone checks before release. [Direct connection](../apps/display-sidecar/src/modules/scrcpy/direct-adb-connection.ts) · [Tunnel selection and startup](../apps/display-sidecar/src/modules/scrcpy/scrcpy.service.ts) · [Display verification](display-streaming.md) · [Upstream scrcpy protocol](https://github.com/Genymobile/scrcpy/blob/v5.0.1/doc/develop.md#connection)

## Implementation order and acceptance gates

First, run a small feasibility spike with the **shipped** sidecar image on native Linux. Prove host USB hotplug and permission scoping, host-key approval, per-transport selection, ADB forwarding, passive scrcpy startup, and invalidation when a TCP peer disappears. Exercise a real phone and an authorized VM. Record the packaged ADB version and actual supported options. The AOSP sources above describe current upstream behavior. If the shipped binary lacks a required capability, pin and verify a compatible platform-tools build as part of the transport slice. This experiment can run before changing public routes.

Land each slice with its consumers and tests. Keep external enrollment disabled until the release checks in slice 6 pass.

### 2. Enroll, attach and retire a connected device

Enrollment uses a separate internal instance of the display sidecar image. This gives USB
access and a persistent key store to the external ADB process while keeping the managed
sidecar and its ADB server isolated. The console exposes the enrollment and connection flows
under `/devices`. Live Linux USB, approved TCP VM and Redroid verification remain
pending. [Deployment configuration](deployment.md#external-android-devices)

The packaged Debian ADB 29.0.6 passed a network-isolated test with two synthetic peers.
The broker's private socket could list transports, read distinct verification values using
their transport IDs, and disconnect a selected peer. A retired relay rejected reconnects,
and the non-root daemon reused its host key after a restart.

- The orchestrator owns registration, desired connection state and admission. The display sidecar owns discovery, ADB host keys, observed transports and the live attachment. Add internal authenticated operations to list eligible USB candidates, open an allowed TCP endpoint, verify/confirm a candidate, inspect current attachment and detach. Expose opaque, short-lived candidate IDs to the enrollment form. The authorized operator confirms the current attempt. An owner with the use privilege may request reconnection, and automation may consume an already confirmed attachment. Operational requests carry device and attachment IDs. Resolve actual ADB targets at the sidecar. Reject a supplied endpoint or serial on operational routes. Validate literal addresses and ports, reject ambiguous inputs and internal service destinations, and keep discovery out of public ingress. [Sidecar ADB routes](../apps/display-sidecar/src/modules/adb/adb.controller.ts) · [Edge routes](../deploy/edge/nginx.conf.template)
- Persist a registration before a bounded connection attempt. Report disconnected, connecting, awaiting Android approval, awaiting operator verification, ready and offline, with a stable failure reason and last observation. Make retries idempotent and enforce unique claims transactionally on endpoint/USB selector and active transport. Prevent aliases from claiming the same observed peer when identity evidence allows it. USB discovery never picks the first available device. For legacy peers without verifiable continuity, require a fresh physical/VM-console confirmation after transport loss. Scripts and saved workflows cannot supply that confirmation.
- Invalidate the old attachment before admitting any new work on reconnect, explicit disconnect, owner change, forget or sidecar/ADB loss. Close viewers, abort/drain admitted work, discard cached observations and ignore late events from the retired generation. A lost monitoring channel invalidates its attachments. Reconcile observations after process restart, fail interrupted reservations, and recover a forgotten device's web metadata cleanup durably. **Acceptance.** Two owners race for one candidate and exactly one wins. Unplug or replace a device at the same endpoint during a queued command. The replacement receives zero commands from the old attachment. [Runtime operation gate](../apps/orchestrator/src/android-apps/common/services/android-apps-runtime-operation-gate.service.ts) · [Identity keys](../apps/orchestrator/src/android-apps/common/utils/android-runtime-identity.ts) · [Cleanup jobs](../apps/web/src/server/persistence/web-maintenance-repository.ts)

### 3. Make viewing and device tools honor the attachment

The external viewer runs in the enrollment broker with its own nginx media paths. A grant
requires the owner and the verified attachment ID. ADB commands select the enrolled transport
through a private listener for that attachment. Disconnect and transport loss close the listener,
pending commands, and display sessions. The viewer opens passively and explicit tools honor
the account's control, clipboard, screenshot, and log permissions.

- Give managed and connected targets separate preparation paths. A connected viewer uses an ADB-server forward for its verified transport. Audit *every* command path, including scrcpy launch, file push, cleanup, focused text, cancellation and retry. Keep listener registration, scrcpy launch, socket-read order, source supervision, media framing and WebRTC fallback intact. Configure external streams to open passively, with keep-awake, automatic power-on and clipboard autosync disabled. Tie manual clipboard access and control to the caller's grant. Treat view-only grants separately on a reused source. Carry the new identity through sidecar session keys, browser stream recovery, activity writes, grant invalidation and casting administration. Release, cancel, prune and revoke remain available during outages or feature shutdown. Build managed-only enumerations for Docker inventory, firewall, quota resource totals, APK retention, volume and inactivity maintenance. **Acceptance.** An offline phone remains registered. Pending and foreign users cannot read the screen. Revocation closes active consumers, and a viewer failure leaves the ADB transport and other viewers usable.
